Fractal — compile a Rails app in place, one file at a time

Fractal is Roundhouse's compile-time optimizer for an app that stays on Rails. You name the files to compile. Fractal reads them and what its passes need to know about the rest of the app, finds work the app's own source makes unnecessary, and rewrites those files. fractal emit writes only changed files at app-relative paths. fractal apply replaces those files in the base app. Rails runs the result with the same gems and line numbers; no complete app copy is created.

Status: early. The pipeline is built, and the pass explorer runs it in your browser. Two passes are registered, inline-delegate and lower-duration, and fractal verify checks an overlay by booting the app before and after it and comparing what Ruby can observe of the compiled code.

▶ Open the pass explorer
  1. Emit the changed files: 
    fractal emit --file app/models/article.rb path/to/app -o out/fractal
  2. Apply them to the base app: 
    fractal apply out/fractal path/to/app

1The idea, simply

Fractal compiles the files you select while the app stays on Rails. It leaves every other file unchanged. A file that no pass changes does not appear in the emitted overlay.

The trick is not doing every chore faster. It is noticing chores that don't need doing at all, like looking up the same fixed recipe every time you cook, when you could write the step down where you use it.

The file is what you compile: --file app/models/article.rb. Emit includes it only when a pass changes it.
An edit is where a rewrite happens: a span of the file replaced, on the same line.
Not sure? Fractal leaves the code as written and says why.

2Fractal removes work. The JIT runs what's left.

Fractal reuses what Roundhouse already knows about an app: which class a name refers to, the types flowing through a method, which definitions exist and where, and what a framework declaration means. It does not convert the app. It edits the app's own Ruby, so the rewritten code is ordinary code that Bootsnap caches and the JIT compiles like any other.

Left to the JIT Inlining calls, type-specialized dispatch, arithmetic, constant folding, faster blocks.
Fractal's job Framework machinery that interprets a description fixed at build time, and methods Rails generates at boot from a description the build already read.

What Fractal has that a JIT does not is the app's source at build time. It can read a description that is fixed once the app is written (an enum mapping, say) and write code that no longer needs to consult it on every call. Because a rewrite is an edit to source, work Rails does at boot (in a class body) and work it does on every call (in a method body) are removed the same way.

3Passes, in order

A JIT like ZJIT does not optimize a method in one big step. It runs a list of small passes, in a fixed order, each doing one thing.

Fractal works the same way, at the level of Ruby source. Each pass reads a compiled file and proposes one kind of edit anywhere in it, or leaves a site alone and says why. The passes always run in the same order, so a build can be read one pass at a time, and new passes can be added one at a time.

What a pass is allowed to do

  • Edit the compiled file, anywhere in it. A class body and a method body are edited the same way.
  • Keep every line where it was. An edit replaces text with text of the same number of lines, so backtraces, coverage and source_location still point at the line a person wrote.
  • Keep the contract. Callers get the same values, exceptions and objects, for every caller in the app as it will run.
  • Check every assumption at build time. The compiled app has no guards and no original to fall back to, so an assumption the build can't check from the app's source and Gemfile.lock is a reason to decline.
  • Decline with a reason whenever it cannot show that its edit behaves like the original.

The driver, not the pass, applies the edits, and it refuses a pass's proposal whole, with a report, when an edit falls outside the file, overlaps another edit or moves a line, or when the rewritten file has a parse error or warning the original did not.

The registered passes

inline-delegate

delegate :name, to: :author makes Active Support build Ruby source for each method at boot and module_eval it. The pass writes that exact source where the call was, on the call's first line, so Rails does not generate it, Bootsnap caches it with the file, and the JIT sees a plain def. It rewrites only the form whose generated source it can reproduce exactly (symbol literals and to: alone, in a class body, with the Active Support version it was checked against, and no app definition of delegate a class body could call instead), and declines everything else with a reason.

lower-duration

5.days.ago builds an ActiveSupport::Duration and two hashes only to call ::Time.current.advance(days: -5), and advance then builds three Dates, another hash and several Rationals to move the zone's wall clock by five days. The pass writes what that comes down to in Ruby's own Time arithmetic, with the number folded: the zone's local time plus 432,000 seconds, wrapped back in the zone as Active Support wraps it (::Time.zone.now.plus_without_duration(-432000)), and ::Time.now.advance(days: -5) when there is no zone. That is 15 objects and 840 bytes a call instead of 37 and 2,456, and about 2.5 times faster under YJIT and ZJIT. Hours, minutes and seconds become ::Time.now.utc + s wrapped once in the zone. Days and weeks stay wall-clock days, so the result across a DST change is the one Rails gives; months and years keep ::Time.current.advance. It rewrites only an integer literal receiver with a unit and direction Active Support defines, inside a method, block or lambda, with the Active Support version it was checked against and no app definition of the methods it takes out, and declines everything else with a reason.

Why the first pass was removed

The first pass, inline-enum-predicates, replaced a call to an Active Record enum predicate (published?) inside the enum's own class with the comparison Rails' generated method runs ((status_for_database == 1)). Rails defines each predicate with a define_method block calling public_send, which ZJIT cannot call directly. rails/rails#59250 proposes plain def predicates so every app can get the benefit without a build step. The proposal remains open; released Rails versions still use block-backed predicates.

4What “done” looks like

Less work Measurably fewer CPU cycles and allocations, with the JIT already on.
Same contract Rails behaviour and every outside caller unchanged; the app's tests pass against the compiled app.
Undo Restore source through version control. Rebuilding does not reverse an applied rewrite.

Apply the overlay, then run the app's test suite on the base app. Build from the same source and Gemfile.lock that the deploy runs. Every transformation is also a trade, so a pass is kept only where the measured trade is worth it.
